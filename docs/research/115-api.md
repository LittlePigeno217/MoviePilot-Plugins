# 115 接口清单（对照 DDSRem-Dev 参考实现）

`AGENTS.md` 要求 115 相关功能对照 [DDSRem-Dev/MoviePilot-Plugins](https://github.com/DDSRem-Dev/MoviePilot-Plugins)
的实现。这份文档把两边的接口面摊开对齐，回答一个问题：**某件事能不能做，走哪条链路做。**

## 来源

读的是真机上装着的那份代码，不是仓库 HEAD（仓库可能更新）：

| 文件 | 行数 | 链路 |
|---|---|---|
| `p115strmhelper/core/u115_open.py` | 1777 | 开放接口（`/open/…`），与本仓库插件同一条路 |
| `p115disk/p115_api.py`（v0.2.30） | 1331 | cookie / web 接口，实现 MoviePilot 的 `StorageBase` |

两个插件都依赖 `p115client==0.0.9.6.5.1`，cookie 侧的调用全部经过这个库。仓库
`docs/p115strmhelper/API_STRM生成功能文档.md` 是**那个插件自己对外提供**的 HTTP 接口文档，
不是 115 上游接口，别找错地方。

## 两条链路

| | 开放接口 | cookie / web 接口 |
|---|---|---|
| 基址 | `https://proapi.115.com/open/…`，登录 `https://passportapi.115.com` | `https://webapi.115.com`、`https://proapi.115.com` 的 android / ios 分支 |
| 凭据 | 设备码换来的 `access_token`（会过期，要刷新） | 登录 Cookie |
| 我们的封装 | `client.py` 的 `_request()` | `client.py` 的 `_request_url()` |
| 覆盖面 | 浏览、上传、下载、复制、删除、改名 | 多出移动、容量、回收站 |

**本仓库插件两条链路都已经在用**（`create_playback_copy` 与 `delete_file` 里就有 `mode` 开关在
两条路之间选），所以补 cookie 侧的接口不是引入新架构，是在既有形状上加方法。

## 只有 cookie 能做的四件事

开放接口里查不到实现，参考实现也一律走 cookie：

1. **移动**（`fs_move`）—— 四处调用点全在 cookie 侧，开放接口没有对应端点
2. **网盘容量**（`fs_index_info`）
3. **回收站列表**（`recyclebin_list`）
4. **回收站还原**（`recyclebin_revert`）

第 3、4 条在参考实现里是**注释掉的代码**（`p115strmhelper/helper/life/client.py:1411-1421`），
也就是连它都没在用，等于没有可参照的实测证据。要做就得自己先探。

不想引 cookie 的话，移动可以用「复制 + 删除」凑（两个我们都有），代价是：换 `file_id`、
丢原时间戳、不是原子操作、大目录慢。作为兜底可以，作为主路径不行。

## 限流与重试：参考实现怎么扛的

`u115_open.py` 的 `_request_api()`（第 174 行起）分四层处理，值得照抄：

| 情形 | 处理 |
|---|---|
| HTTP 429 | 读响应头 `X-RateLimit-Reset`，再加 5 秒，睡完重试 |
| 其它 HTTP 错误 | 指数退避 `2 ** (5 - 剩余次数 + 1)` 秒，最多重试 5 次 |
| 业务 `code != 0` | 打 `message` 后返回 None |
| `message` 含「已达到当前访问上限」 | 固定等 `retry_delay = 70` 秒重试，独立于上面那条退避 |

另外两个分散限流的手法：

- **改名随机三选一**（`u115_open.py:1170`）：`randint(0, 2)` 在「开放接口 / `fs_rename` /
  `fs_rename_app`」之间轮换，把同一种操作摊到三个端点上
- **移动两端点交替 + 专用限流器**（`p115_api.py:1218`）：`_move_call_counter % 2` 在
  `fs_move` 与 `fs_move_app` 之间交替，外面还套了一个只管移动的 `_move_rate_limiter`

## 全树遍历与缓存

- `u115_open.py` 有三个遍历器：`iter_files_with_path_simple`、`iter_files_with_path`、
  `iter_files_with_path_inc`（**增量**）。要做全库体检就照这个来，不用从零写。
- 参考实现用 **alembic 管的数据库表**缓存 115 目录树（`db_manager/models/open_file.py`、
  `open_folder.py`，版本文件在 `database/versions/`），不是每次现查。几万条记录靠
  `plugindata` 那个 json 列扛不住 —— 那一列每次读写都是整份序列化。

## 一个可能省掉整块工作量的事实

`p115disk/p115_api.py` 实现的是 MoviePilot 的 `StorageBase`：`list` / `create_folder` /
`get_item` / `delete` / `rename` / `download` / `upload` / `detail` / `copy` / `move` /
`usage` / `support_transtype`。**它把 115 注册成了宿主的一个存储**，于是浏览、改名、移动、
删除都用 MoviePilot 自己的文件管理界面，插件不必再画一个。

所以「在我们插件里做网盘管理界面」之前，先确认宿主那套够不够用。

## 对本仓库插件的适配结论

| 要做的 | 怎么做 | 工作量 |
|---|---|---|
| 改名 | 开放接口加一个方法：`POST /open/ufile/update` `{file_id, file_name}` | 一个方法 |
| 移动 | cookie 侧加 `web_move_url`，形状照 `files/copy`（`fid` + `pid`），**先真机实测** | 一个方法 + 一次实测 |
| 网盘容量 | cookie 侧 `fs_index_info` 的等价 URL，未实测 | 一次实测 |
| 回收站列表 / 还原 | 两个端点都未实测，先探明再决定放不放进界面 | 两次实测 |
| 全库体检 | 遍历照 `iter_files_with_path_inc`；缓存要建表，不能用 plugindata | 大 |

**一条硬规矩**：`/open/rb/del` 不带 `tid` 会清空整个回收站。任何时候都不要出现无参调用，
封装时把 `tid` 设成必填。
